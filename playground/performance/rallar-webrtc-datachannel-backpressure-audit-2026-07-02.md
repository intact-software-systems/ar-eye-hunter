## Scope

This audit focuses on WebRTC `RTCDataChannel` performance and backpressure behavior:

- DataChannel creation and lane configuration
- ordered/unordered and reliable/unreliable channels
- send loops, `bufferedAmount`, and `bufferedAmountLowThreshold`
- retry queues, DataChannel queues, and AL/outbox queues
- JSON/binary serialization, parsing, copies, and large payload behavior
- per-peer fanout and room broadcast behavior
- disconnect/reconnect cleanup of queues, handlers, and listeners

Labels:

- `Proven from code`: directly visible in source.
- `Strong suspicion`: likely from source shape, but runtime impact depends on workload.
- `Needs runtime measurement`: static analysis cannot prove impact.

| --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Can sends continue while `bufferedAmount` is high?                                | Native `dc.send()` is avoided by `QRtcDataChannel.sendRaw()` once `bufferedAmount >= highWatermarkBytes`; it drops, replaces, or queues instead. Producers can still call send continuously because the API returns immediately. Higher-level `send()` and `sendAsJsonString()` hide `dropped`, `queued`, and `replaced` results. See [`QRtcDataChannel.sendRaw`](../../packages/shared/webrtc/QRtcDataChannel.ts#L253), [`handleBackPressure`](../../packages/shared/webrtc/QRtcDataChannel.ts#L613), and [`sendRawOrThrow`](../../packages/shared/webrtc/QRtcDataChannel.ts#L567).                                                                                                                                              |
| Are messages queued without a bound?                                              | The `QRtcDataChannel` queue is bounded by `flowControl.maxQueueItems`, default 32. Configured lanes use finite bounds. However, custom `maxQueueItems` has no visible clamp, and AL/outbox durable effects can accumulate separately when producers outpace drain. See [`DEFAULT_FLOW_CONTROL`](../../packages/shared/webrtc/QRtcDataChannel.ts#L118), [`enqueueQueuedSend`](../../packages/shared/webrtc/QRtcDataChannel.ts#L658), and [`ALOutboundMessageRuntime`](../../packages/shared/alm/ALOutboundMessageRuntime.ts#L211).                                                                                                                                                                                                 |
| Is there a drop/coalesce policy for high-frequency messages?                      | Yes in the wrapper: `drop-new`, `drop-old`, `replace-by-key`, and `queue`. Realtime/game lanes use `replace-by-key` for pose/input/snapshot-like traffic, `drop-old` for metrics, and `queue` for reliable intent/replication. See [`RtcDataChannelOverflowMode`](../../packages/shared/webrtc/QRtcDataChannel.ts#L32), [`DEFAULT_REALTIME_DATA_CHANNEL_LANE`](../../packages/shared-web/browser/middleware.ts#L72), and [`createRallarGameLanePresets`](../../packages/shared-web/game/lanes.ts#L24).                                                                                                                                                                                                                            |
| Are large payloads copied, encoded, stringified, or base64-encoded unnecessarily? | JSON realtime sends stringify per peer. AL message validation stringifies and `TextEncoder`-measures payloads before message creation, then QueueBox serialization stringifies whole messages. Binary send passes `ArrayBuffer`/views directly, but binary receive copies views and blobs to `ArrayBuffer`. No base64 layer is visible in the DataChannel send path. See [`QRtcDataChannel.sendJson`](../../packages/shared/webrtc/QRtcDataChannel.ts#L239), [`validateRallarJsonPayload`](../../packages/shared/api/rallar-validation.ts#L244), [`QueueBoxUtilities.toResourceEntryFromMsg`](../../packages/shared/services/QueueBoxUtilities.ts#L79), and [`toArrayBuffer`](../../packages/shared-web/browser/rallar.ts#L9704). |
| Is the same message serialized once or once per peer?                             | Direct realtime JSON fanout serializes once per peer because each peer calls `laneOpen.channel.sendJson(input.data, ...)`, and `sendJson()` calls `JSON.stringify`. AL/outbox sends may serialize per prepared immediate send, while persisted outbox sends can reuse `entry.resource`. See [`sendRealtimeJson`](../../packages/shared-web/browser/rallar.ts#L3918), [`QRtcDataChannel.sendJson`](../../packages/shared/webrtc/QRtcDataChannel.ts#L239), [`WebRtcOverlayMulticastManager.sendPreparedMessage`](../../packages/shared/multicast/WebRtcOverlayMulticastManager.ts#L586), and [`WebRtcRxStreamerService.enableDefaultCallbacks`](../../packages/shared/services/WebRtcRxStreamerService.ts#L188).                    |
| Are broadcasts `O(peers)`, `O(peers x message size)`, or worse?                   | Direct realtime room sends are `O(readyPeers x message size)` due per-peer JSON serialization and per-peer lane-open/send work. Overlay/AL sends are `O(nextHopMessages x message size)` plus admission-store and retry/effect overhead. See [`sendRoomRealtimeJson`](../../packages/shared-web/browser/rallar.ts#L5207), [`sendRealtimeJson`](../../packages/shared-web/browser/rallar.ts#L3918), and [`WebRtcOverlayMulticastManager.toOutboundDispatchPlan`](../../packages/shared/multicast/WebRtcOverlayMulticastManager.ts#L524).                                                                                                                                                                                           |
| Are queues cleared on channel close?                                              | `reset()` clears queued sends. The native `dc.onclose` handler clears event handlers and the native `dc` reference, but does not call `clearQueuedSends()`. Queued payloads can remain on the wrapper until peer reset or later flushing/stale-drop. See [`QRtcDataChannel.reset`](../../packages/shared/webrtc/QRtcDataChannel.ts#L161), [`dc.onclose`](../../packages/shared/webrtc/QRtcDataChannel.ts#L456), and [`clearQueuedSends`](../../packages/shared/webrtc/QRtcDataChannel.ts#L704).                                                                                                                                                                                                                                   |
| Are event handlers removed on close?                                              | Native DataChannel handlers are nulled in `clearDataChannelReference()`, which is called on close and reset. Wrapper callback maps are separate and are not cleared by `reset()`. See [`clearDataChannelReference`](../../packages/shared/webrtc/QRtcDataChannel.ts#L525), [`dc.onclose`](../../packages/shared/webrtc/QRtcDataChannel.ts#L456), and [`clearCallbacks`](../../packages/shared/webrtc/QRtcDataChannel.ts#L168).                                                                                                                                                                                                                                                                                                    |
| Could reconnects duplicate channels or listeners?                                 | Same-wrapper reconnect uses a stable `dataChannelCallbackId()` and closes a mismatched existing native channel, reducing duplicate-listener risk. The unclear part is queued payload/callback lifetime across close/reconnect because `onclose` does not clear queued sends and `reset()` does not clear callback maps. See [`QRtcDataChannel.connect`](../../packages/shared/webrtc/QRtcDataChannel.ts#L341), [`dataChannelCallbackId`](../../packages/shared/webrtc/QRtcDataChannel.ts#L537), and [`WebRtcConnectionService.computeRtcPeerDtoIfAbsent`](../../packages/shared/services/WebRtcConnectionService.ts#L932).                                                                                                        |

## DataChannel Flow Summary

### Creation And Lanes

- `WebRtcConnectionService.createDataChannels()` creates one `QRtcDataChannel` wrapper per configured lane and passes `RTCDataChannelInit`, `binaryType`, and `flowControl` through to the wrapper. See [`createDataChannels`](../../packages/shared/services/WebRtcConnectionService.ts#L1285).
- If no explicit `reliable` lane is provided, `dataChannelLanes()` prepends a default reliable lane using browser defaults, which means ordered and reliable by default. See [`DEFAULT_RTC_DATA_CHANNEL_LANE_ID`](../../packages/shared/services/WebRtcConnectionService.ts#L105) and [`dataChannelLanes`](../../packages/shared/services/WebRtcConnectionService.ts#L1310).
- `QRtcDataChannel.connect()` creates the native channel on initiators with `peerConnection.createDataChannel(label, init)` and waits for `pc.ondatachannel` on receivers. See [`QRtcDataChannel.connect`](../../packages/shared/webrtc/QRtcDataChannel.ts#L341) and [`QRtcPeerConnection.createDataChannel`](../../packages/shared/webrtc/QRtcPeerConnection.ts#L404).
- The default realtime lane is unordered and unreliable (`ordered: false`, `maxRetransmits: 0`) with `replace-by-key` overflow. See [`DEFAULT_REALTIME_DATA_CHANNEL_LANE`](../../packages/shared-web/browser/middleware.ts#L72).
- Game lanes separate traffic by semantics: input/snapshot/metrics are unordered unreliable, while intent/replication are ordered reliable. See [`createRallarGameLanePresets`](../../packages/shared-web/game/lanes.ts#L24) and the AR Eye Hunter lane overrides in [`ARENA_RALLAR_GAME_DATA_CHANNEL_LANES`](../../apps/ar-eye-hunter-v1/src/game/rallar-game-match-adapter.ts#L32).

### Send Path

- Direct realtime JSON flow: `rallar.realtime.sendJson()` -> `sendRealtimeJson()` -> per peer `ensureRealtimeLaneOpen()` -> `QRtcDataChannel.sendJson()` -> `sendRaw()`. See [`sendRealtimeJson`](../../packages/shared-web/browser/rallar.ts#L3918), [`ensureRealtimeLaneOpen`](../../packages/shared-web/browser/rallar.ts#L8221), and [`QRtcDataChannel.sendJson`](../../packages/shared/webrtc/QRtcDataChannel.ts#L239).
- Direct realtime room flow resolves room peers, waits for ready peers, then calls `sendRealtimeJson()` with `readyPeerIds`. See [`sendRoomRealtimeJson`](../../packages/shared-web/browser/rallar.ts#L5207) and [`resolveRealtimePeerIds`](../../packages/shared-web/browser/rallar.ts#L8196).
- AL/room message flow creates an `ALMessage`, enqueues through `rtcRxStreamer.enqueueOutboxIfAbsent()`, and sends through `WebRtcOverlayMulticastManager`. See [`sendRtcMessage`](../../packages/shared-web/browser/rallar.ts#L3566), [`WebRtcRxStreamerService.enqueueOutboxIfAbsent`](../../packages/shared/services/WebRtcRxStreamerService.ts#L395), and [`WebRtcOverlayMulticastManager.enqueueIfAbsent`](../../packages/shared/multicast/WebRtcOverlayMulticastManager.ts#L119).
- DataChannel backpressure flow: `sendRaw()` first flushes queued sends, checks `bufferedAmount`, then either sends immediately or applies the overflow policy. See [`sendRaw`](../../packages/shared/webrtc/QRtcDataChannel.ts#L253), [`flushQueuedSends`](../../packages/shared/webrtc/QRtcDataChannel.ts#L672), and [`isBackPressured`](../../packages/shared/webrtc/QRtcDataChannel.ts#L795).

### Receive Path

- Raw realtime callbacks are installed per peer/lane via `onRawMessageDo()`, then JSON strings are parsed in `dispatchRealtimeJson()` and binary payloads are normalized in `dispatchRealtimeBinary()`. See [`registerRealtimeCallbacksForPeer`](../../packages/shared-web/browser/rallar.ts#L7996), [`dispatchRealtimeJson`](../../packages/shared-web/browser/rallar.ts#L8037), and [`dispatchRealtimeBinary`](../../packages/shared-web/browser/rallar.ts#L8065).
- AL/RTC messages use `onRtcMessageDo()`, so `QRtcDataChannel` parses JSON once before dispatching typed callbacks. See [`QRtcDataChannel.onmessage`](../../packages/shared/webrtc/QRtcDataChannel.ts#L412) and [`WebRtcRxStreamerService.addPeer`](../../packages/shared/services/WebRtcRxStreamerService.ts#L104).

## Room Broadcast Behavior

- Direct realtime room send:
  - Resolves `desiredPeerIds`, waits for ready peers if needed, then sends directly to `readyPeerIds`. See [`sendRoomRealtimeJson`](../../packages/shared-web/browser/rallar.ts#L5207).
  - Uses `Promise.all(peerIds.map(...))`, so all peer sends are attempted concurrently. See [`sendRealtimeJson`](../../packages/shared-web/browser/rallar.ts#L3925).
  - Serializes JSON once per peer. Complexity is `O(readyPeers * message size)` plus lane-open checks.
- Targeted channel send:
  - Resolves peer IDs and calls `realtime.sendJson()` with those peers. See [`createTargetedChannel`](../../packages/shared-web/browser/rallar.ts#L5347).
- AL/overlay room message send:
  - Creates an `ALMessage`, plans overlay forwarding, and creates one prepared transport message per next hop. See [`sendRtcMessage`](../../packages/shared-web/browser/rallar.ts#L3566), [`createDirectDispatchPlan`](../../packages/shared/multicast/WebRtcOverlayMulticastManager.ts#L423), and [`toOutboundDispatchPlan`](../../packages/shared/multicast/WebRtcOverlayMulticastManager.ts#L524).
  - Immediate sends call `peer.channel.send(msg)`, which stringifies the prepared message. See [`sendPreparedMessage`](../../packages/shared/multicast/WebRtcOverlayMulticastManager.ts#L586) and [`QRtcDataChannel.send`](../../packages/shared/webrtc/QRtcDataChannel.ts#L234).
  - Persisted outbox sends can reuse the pre-serialized `entry.resource`. See [`QueueBoxUtilities.toResourceEntryFromMsg`](../../packages/shared/services/QueueBoxUtilities.ts#L79) and [`WebRtcRxStreamerService.enableDefaultCallbacks`](../../packages/shared/services/WebRtcRxStreamerService.ts#L188).

## Disconnect And Reconnect Behavior

- Peer removal explicitly calls `channel.reset()` for every channel, then resets the peer connection and deletes the peer DTO. This clears `sendQueue` on normal removal. See [`WebRtcConnectionService.removePeerIfPresent`](../../packages/shared/services/WebRtcConnectionService.ts#L305).
- Native DataChannel close does not clear `sendQueue`, only native handlers/reference. See [`dc.onclose`](../../packages/shared/webrtc/QRtcDataChannel.ts#L456) and [`clearDataChannelReference`](../../packages/shared/webrtc/QRtcDataChannel.ts#L525).
- Reconnect can reuse an existing peer DTO if the peer connection is connected/connecting/new and has reconnectable channels. See [`hasReconnectableDataChannels`](../../packages/shared/services/WebRtcConnectionService.ts#L850) and [`computeRtcPeerDtoIfAbsent`](../../packages/shared/services/WebRtcConnectionService.ts#L932).
- `QRtcDataChannel.connect()` uses the same `dataChannelCallbackId()` for a peer/lane and closes a different existing native channel before replacing it. This limits duplicate native channel/listener accumulation for the same wrapper. See [`QRtcDataChannel.connect`](../../packages/shared/webrtc/QRtcDataChannel.ts#L341) and [`dataChannelCallbackId`](../../packages/shared/webrtc/QRtcDataChannel.ts#L537).
- Realtime raw callbacks are removed on peer deletion and when a lane has no listeners. See [`registerRealtimeLifecycleCallback`](../../packages/shared-web/browser/rallar.ts#L7959) and [`deleteRealtimeLaneIfUnused`](../../packages/shared-web/browser/rallar.ts#L8105).

## Top Measurement Tasks

1. **Backpressure fanout test.** In a room with 2, 5, and 10 peers, send fixed-size realtime JSON payloads at increasing rates on the realtime and game snapshot lanes. Record `bufferedAmount`, queue length, dropped/replaced counts, send latency, and CPU time.
2. **Close/reconnect queue retention test.** Force a lane into backpressure until queued items exist, close the native DataChannel without full peer removal, reconnect, then send one new message. Verify whether old queued payloads remain, stale-drop, or flush.
3. **AL vs realtime serialization test.** Send the same payload through direct realtime room sends and typed `messages.rtc` room sends. Count serialization calls, total serialized bytes, outbox/effect depth, and delivery status under not-ready and congested peers.
