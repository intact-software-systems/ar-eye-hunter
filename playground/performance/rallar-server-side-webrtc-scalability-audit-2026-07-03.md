# Server-Side WebRTC Scalability Audit

Date: 2026-07-03

Scope: static analysis of server-side WebRTC-adjacent code paths for rooms, participants, sessions, peer maps, signaling fanout, ICE candidate relay, topology/relay decisions, WebSocket connection handling, reconnect/leave/disconnect cleanup, and per-room/per-participant data structures. No benchmarks or runtime profiling were run. No production code was changed.

## Executive Summary

The server-side WebRTC role in this repository is signaling, state sync, durable message delivery, room/session presence, and RTC topology computation. A scoped static search of `packages/**`, `apps/api-v1`, `apps/rallar-black-box-control-server`, and `apps/rallar-black-box-headless` did not identify a server-side SFU/MCU media-forwarding pipeline, recording pipeline, or transcription pipeline. The relevant server-side paths are WebSocket relay and room topology paths such as `packages/shared-server/rallar-system/ws-system-topics.ts:initRtcSignalingTopic`, `packages/shared/services/WsQueueBoxServerService.ts`, and `packages/shared-server/rallar-system/services/rallar-rtc-topology-service.ts`.

## Scalability Model

Variables used below:

| Symbol     | Meaning                                          |
| ---------- | ------------------------------------------------ |
| `R`        | number of rooms/groups                           |
| `P`        | active participants/sessions in one room         |
| `C`        | open WebSocket connections in one server process |
| `S_client` | retained client session rows/snapshots           |
| `S_group`  | retained group presence session rows             |
| `M`        | group members                                    |
| `T_rtt`    | retained RTT measurements                        |
| `Q`        | QueueBox/resource-inbox rows                     |
| `H`        | dynamic topic handlers/proxy rules/definitions   |

Server-side WebRTC flow:

1. A WebSocket is upgraded in `apps/api-v1/src/routes/ws-routes.ts` at `handleWsRoute` lines 7-56 and registered in `packages/shared/websocket/JsonWebSocketServer.ts:addConnection` lines 65-73.
2. WebSocket lifecycle cleanup is installed by `apps/api-v1/src/create-rallar-server.ts:createRallarServer` lines 78-108 through `packages/shared-server/rallar-system/services/ws-lifecycle-service.ts:initWsLifecycle` lines 14-49.
3. WebRTC signaling uses either the legacy `rtcSignaling` system topic in `packages/shared-server/rallar-system/ws-system-topics.ts:initRtcSignalingTopic` lines 739-759 or QueueBox-backed signaling through `packages/shared/webrtc/WsRtcSignalingTransportUsingWsQBox.ts:send` lines 71-84 and `packages/shared/services/WsQueueBoxServerService.ts`.
4. Room-scoped WebSocket topics are routed by `packages/shared-server/rallar-facade/ws-topic-router.ts:handle` lines 360-470, authorized through `apps/api-v1/src/services/ws-topic-room-authorizer.ts:createWsTopicRoomAuthorizer` lines 8-23 and `packages/shared-server/rallar-system/services/ws-topic-room-authorizer.ts:createGroupRoomWsAuthorizer` lines 29-99.
5. Room/session state is written through `packages/shared-server/rallar-system/services/group-state-service.ts` and published through `packages/shared-server/rallar-system/services/AppGroupInboxService.ts:publishGroupMutation` lines 533-549.
6. RTC overlay topology is updated from group state and RTT messages in `packages/shared-server/rallar-system/ws-system-topics.ts:updateRtcOverlayTopology` lines 326-357, `initRttTopic` lines 670-708, and `packages/shared-server/rallar-system/services/rallar-rtc-topology-service.ts:updateGroupTopology` lines 164-246.

## Recommended Load-Test Scenarios

1. Large-room topology scaling: create one room with `P = 2, 4, 8, 16, 32, 64` active sessions, emit group joins/leaves and RTT updates, and measure `RallarRtcTopologyService.updateGroupTopology` duration, graph edge count, topology snapshot size, heap growth, and event-loop delay. ## Static Conclusions

- Join, leave, reconnect, broadcast, participant update, and cleanup are not uniformly O(room peers). Several critical paths scale with retained global sessions or all client snapshots, especially `state-sync-routing.resolveGroupRecipients`, `client-state-service.findClientSessionBySessionId`, and `group-state-service.disconnectPresenceSessionsBySessionIdWritten`.
- Server-side fanout is usually O(recipients), with some optimized one-serialization paths. Durable outbox fanout is heavier because it creates recipient-specific prepared messages/effects and can serialize once per recipient.
- Room state does grow after participants leave by design for purge grace. This is visible in `session-expiry.ts:toSessionPurgeAfterEpochMs` lines 5-19 and should be treated as retained state, not necessarily a leak.
- Closed sockets are removed from `JsonWebSocketServer.connections` on the close event, but slow open sockets have no visible backpressure policy.
- Server-side queues have bounded dequeue/drain loops, but static analysis did not find a clear per-room/per-peer producer-side queue cap.
- One participant can plausibly degrade a large room by causing RTT/topology work or by acting as a slow recipient during fanout. This remains a runtime hypothesis until measured.

## Recommended First Measurement

Start with the large-room topology and cleanup tests. They have the clearest static complexity signal and are likely to produce actionable data without needing a full browser media stack:

1. Measure `RallarRtcTopologyService.updateGroupTopology` at 8/16/32/64 peers with and without RTT data.
2. Measure abrupt socket close cleanup latency against retained `S_client` and `S_group` counts.
3. Add a slow-client fanout test that records `bufferedAmount`, send duration, QueueBox age, and heap/RSS over time.
