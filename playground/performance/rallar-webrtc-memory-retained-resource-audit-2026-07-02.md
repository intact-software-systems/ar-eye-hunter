## Scope

This audit focuses on WebRTC retained resources and leak-shaped lifecycle risks in:

- `RTCPeerConnection` and peer DTO lifecycle
- `RTCDataChannel` lifecycle, send queues, callbacks, and open waiters
- media streams, tracks, senders, receivers, and transceivers
- ICE candidate queues, pending signaling chains, reconnect timers, and retry state
- WebSocket client/server sockets, listeners, reconnect logic, and signaling ownership
- room/session/participant maps and retained peer state
- stats, telemetry, heartbeat intervals, and long-lived callbacks
- server-side forwarding, topology, and overlay multicast state where it intersects RTC

Labels:

- `Proven from code`: the lifecycle or cleanup behavior is directly visible in code.
- `Strong suspicion`: code shape suggests a retained-resource risk, but runtime behavior decides impact.
- `Needs runtime measurement`: static analysis cannot prove whether the object is retained or collected.

Release columns:

- `Normal`: ordinary close/disconnect.
- `Error`: error or failed event.
- `Reconnect`: disconnect/reconnect/ICE restart churn.
- `Shutdown`: navigation, facade disconnect, or app shutdown.
- Values: `Y` covered, `P` partial, `?` requires runtime proof.

## Executive Summary

Top retained-resource risks:

1. **Reconnect timers can accumulate stale disconnect callbacks.** `QRtcPeerConnection.setupStateChangeCallbacks()` overwrites `status.disconnectTimer` each time the PC reports `disconnected` without clearing an existing disconnect timer, while `connected` clears only `reconnectTimer`. See [`QRtcPeerConnection.setupStateChangeCallbacks`](../../packages/shared/webrtc/QRtcPeerConnection.ts#L328) and [`closePeerConnectionIfPresent`](../../packages/shared/webrtc/QRtcPeerConnection.ts#L133). Severity: high, confidence: proven from code.
2. **DataChannel callback maps survive `reset()`.** `QRtcDataChannel.reset()` closes the channel and clears queued sends, but does not call `clearCallbacks()`. If the channel object remains reachable through peer/group/facade state, registered closures remain reachable too. See [`QRtcDataChannel.reset`](../../packages/shared/webrtc/QRtcDataChannel.ts#L161), [`clearCallbacks`](../../packages/shared/webrtc/QRtcDataChannel.ts#L168), and callback maps at [`QRtcDataChannel`](../../packages/shared/webrtc/QRtcDataChannel.ts#L139). Severity: high, confidence: proven from code.
3. **ICE candidate queue is bounded only by remote-description progress or peer reset.** Candidates received before `remoteDescription` are pushed to `status.iceCandidateQueue` with no cap or dedupe, then flushed after descriptions land. See [`processSignal`](../../packages/shared/webrtc/QRtcPeerConnection.ts#L430) and [`flushIceCandidateQueue`](../../packages/shared/webrtc/QRtcPeerConnection.ts#L525). Severity: medium/high, confidence: proven from code.
4. **WebSocket listener cleanup relies on socket close and GC.** `JsonWebSocketClient.openSocket()` and `JsonWebSocketServer.addAllEventListeners()` attach anonymous listeners; `JsonWebSocketClient.close()` closes and clears `ws`, but does not remove listeners. Impact depends on whether old sockets remain reachable. See [`JsonWebSocketClient.openSocket`](../../packages/shared/websocket/JsonWebSocketClient.ts#L100), [`JsonWebSocketClient.close`](../../packages/shared/websocket/JsonWebSocketClient.ts#L242), and [`JsonWebSocketServer.addAllEventListeners`](../../packages/shared/websocket/JsonWebSocketServer.ts#L75). Severity: medium, confidence: needs runtime measurement.
5. **Local media capture stores the runtime before attach completes.** `startMediaSource()` stores an open stream runtime and registers track-ended listeners before awaiting `handle.attach()`. If attach fails, the captured stream may remain in `localMediaSources` until explicit stop/shutdown. See [`startMediaSource`](../../packages/shared-web/browser/rallar.ts#L5427), [`stopMediaSource`](../../packages/shared-web/browser/rallar.ts#L5560), and [`shutdownApiMiddleware`](../../packages/shared-web/browser/rallar.ts#L9873). Severity: medium, confidence: strong suspicion.

## Cleanup Gaps And Unclear Ownership

- `QRtcDataChannel.reset()` releases native channel refs and queues, but not callback maps. See [`QRtcDataChannel.reset`](../../packages/shared/webrtc/QRtcDataChannel.ts#L161) and [`clearCallbacks`](../../packages/shared/webrtc/QRtcDataChannel.ts#L168).
- `QRtcPeerConnection` has explicit PC handler cleanup, but pending `signalingChain` and `outboundSignalingChain` are not reset or aborted. See [`QRtcPeerConnection`](../../packages/shared/webrtc/QRtcPeerConnection.ts#L82), [`handleSignal`](../../packages/shared/webrtc/QRtcPeerConnection.ts#L418), and [`sendSignal`](../../packages/shared/webrtc/QRtcPeerConnection.ts#L599).
- `disconnectTimer` ownership is unclear because the helper [`stopReconnectTimer`](../../packages/shared/webrtc/QRtcPeerConnection.ts#L647) clears `disconnectTimer`, but the state transition path does not call it.
- `JsonWebSocketClient.close()` does not remove socket listeners, and callback registry maps remain owned by the client object. See [`JsonWebSocketClient.close`](../../packages/shared/websocket/JsonWebSocketClient.ts#L242).
- `WebRtcGroupManager` intentionally retains peers across group deletes when `retainConnections` is enabled, but the retention budget should be observed at runtime. See [`delete`](../../packages/shared/services/WebRtcGroupManager.ts#L84) and [`retainKnownPeersForGroup`](../../packages/shared/services/WebRtcGroupManager.ts#L330).
- `RallarRtcTopologyService` has long-lived maps by overlay ID and no cleanup path found in this scoped search. See [`RallarRtcTopologyService`](../../packages/shared-server/rallar-system/services/rallar-rtc-topology-service.ts#L60).

## Error And Reconnect Cleanup Risks

- DataChannel `onerror` marks state failed and resolves open waiters, but does not close or clear the native channel reference immediately. See [`QRtcDataChannel.setupDataChannelCallbacks`](../../packages/shared/webrtc/QRtcDataChannel.ts#L477). This may be correct if close follows, but it should be validated.
- Peer reconnect uses `restartIce()` from both automatic reconnect [`QRtcPeerConnection.handleReconnect`](../../packages/shared/webrtc/QRtcPeerConnection.ts#L537) and facade recovery [`restartRtcIce`](../../packages/shared-web/browser/rallar.ts#L6353). Runtime validation should verify no renegotiation/restart storm creates unbounded pending work.
- `waitForRtcChannelOpenOrAbort()` removes abort listeners on success/failure and abort, which is a good cleanup path. See [`waitForRtcChannelOpenOrAbort`](../../packages/shared/services/WebRtcConnectionService.ts#L1390). Keep this as a baseline when instrumenting open waiter counts.
- Shutdown is reasonably comprehensive: [`shutdownApiMiddleware`](../../packages/shared-web/browser/rallar.ts#L9873) stops heartbeats, disconnects known peers, stops local media, disposes overlay multicast, stops qbox engine, and closes the WebSocket queue. The main remaining question is whether all pending async callbacks settle after shutdown.

## Do Not Optimize Yet: Validation Plan

The next phase should prove or disprove retained-resource hypotheses before changing behavior.

1. Add temporary debug counters behind a dev flag or test harness, not production-visible behavior:
   - active peer DTO count
   - active PC count by `connectionState`
   - DataChannel native ready states
   - DataChannel callback map sizes
   - DataChannel sendQueue and openWaiter counts
   - ICE queue length and duplicate-candidate count
   - heartbeat service count and interval schedule/clear counts
   - reconnect/disconnect timer schedule/clear/fire counts
   - WebSocket open/close/error counts and reconnect task count
   - local media source count and track `readyState`
   - retained group peer count and topology snapshot count
2. Use heap snapshots after forced GC in browser/dev runtime:
   - filter constructors: `RTCPeerConnection`, `RTCDataChannel`, `MediaStream`, `MediaStreamTrack`, `WebSocket`, `QRtcPeerConnection`, `QRtcDataChannel`, `WebRtcHeartbeatService`
   - inspect retaining paths for callback maps, timers, promises, room maps, and socket listeners
3. Record counts at four lifecycle points:
   - after connect and media attach
   - after ICE restart/reconnect churn
   - after peer removal/room leave
   - after full `rallar.disconnect()`/shutdown
4. Treat a leak as confirmed only when object counts or retained heap grow monotonically across repeated cycles and do not return to baseline after cleanup and forced GC.

## Top 3 Measurement Tasks To Run Next

1. **Reconnect churn retained-resource test.** Two or three browser clients join one room, establish RTC lanes, then force repeated `disconnected`, `failed`, and `restartIce()` cycles. Capture disconnect/reconnect timer counts, pending signaling chain age, ICE queue max length, and heap snapshots.
2. **DataChannel lifecycle callback test.** Create and remove peers/lanes repeatedly. After each removal, assert peer DTO count, DataChannel callback map sizes, open waiter count, sendQueue length, and heartbeat callback count return to baseline.
3. **Media attach failure and shutdown test.** Force `getUserMedia`/`getDisplayMedia` success followed by `attachLocalMediaSources()` failure, then call stop and disconnect paths. Verify tracks stop, `localMediaSources` is empty, and no stopped tracks remain attached to senders.

## Minimal Leak Reproduction Scenario

1. Open two browser clients in the same room.
2. Establish a WebRTC peer connection, one DataChannel lane, microphone/camera, and optionally screen sharing.
3. Loop 100 times:
   - send several DataChannel messages
   - call facade ICE restart for the peer
   - briefly block or close signaling/WebSocket to trigger reconnect paths
   - leave/rejoin or remove/recreate the peer
4. Every 10 iterations record:
   - known peer IDs and active peer IDs
   - PC `connectionState`
   - DataChannel ready state, sendQueue length, callback counts, openWaiters
   - ICE queue length
   - heartbeat service count and interval count
   - local media source count and track `readyState`
   - WebSocket ready state and reconnect task count
5. After the loop, call full disconnect/shutdown, force GC, and take a heap snapshot.
6. Confirm or refute retention of closed `RTCPeerConnection`, closed `RTCDataChannel`, old `WebSocket`, stopped `MediaStreamTrack`, stale heartbeat services, and callback closures.

## Proposed Order Of Fixes After Validation

Do not optimize or change behavior until the measurements above identify confirmed retained resources. If confirmed, fix in this order:

1. Timer and callback ownership: clear duplicate `disconnectTimer` paths and decide/reset DataChannel callback lifetime.
2. Queue and async lifetime: cap/dedupe ICE candidate queue if candidate growth is real; add generation or abort checks to signaling chains only if stale chains persist.
3. Media lifecycle: stop and remove captured streams when attach fails; detach absent sender kinds only if stopped tracks remain attached.
4. Socket lifecycle: store and remove WebSocket listener refs only if heap snapshots show old sockets/listeners retained.
5. Room/server caches: add TTL or explicit cleanup for topology and retained peer maps only if high-cardinality room/overlay tests prove growth.
