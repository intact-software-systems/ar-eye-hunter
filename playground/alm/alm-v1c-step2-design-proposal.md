# ALM Release 7 V1c step 2: the setup burst, the leader-ACK path and the harness at scale

V1c step 1 (#652) delivered bounded lane service and the consumer-proof workload; the original
capture-off 15-agent acceptance still fails at setup (HTTP timeouts at the 5,000 ms command limit
behind a 35 s AppInbox queue) and in traffic (84 shots arrive at the director, 15–71 leader-ACK
observers time out inside the 30 s window). This proposal records the static performance audit of
2026-10-14, the GitHub Free review, the decisions D194 to D204 and the split of step 2 into two
slices. It implements the maintainer's standing constraints in
[the V1c plan](../../plans/active/alm-v1c-scale-evidence-implementation-plan.md): both the Rallar
production code and the black-box harness are slow at scale, the queuebox engine is the
event-handling core and must stay quick and fault tolerant, the recipes run locally first, and no
legacy, duplication or migration code is added.

## 1. Static audit

Five read-only audits ran against `main` at `2d5ffe35f` (static analysis as hypothesis generation
under the `performance-analysis` skill; every row carries a confidence label; nothing below was
measured unless it says so). The hosted API is one `prod-in-memory` Deno process with in-process
PGlite: SQL runs on the handler's JavaScript thread under an exclusive transaction lock, so every
statement, poll and serialization is event-loop time, and more worker concurrency adds no CPU there.

### 1.5 Where the time goes (hypothesis chains to confirm by measurement)

- **Setup burst (35 s queue age, HTTP 503 at 5 s):** serial handlers (F4) × per-handler cost
  (W1–W3, ≈3.7 s hosted) + idle gaps between batches (F1) + a serialized database shared with
  O(sessions) status polls (F3) and 4 redundant statements per entry (F2), on a host also running
  the control server's O(A·N³) rollups (H1).
- **Local baseline (this Mac, 2026-10-14, all-local lifecycle, memory API, 15 agents):** every page
  sets up and reaches traffic; the run fails in the players' 30 s windows with 240
  `ALM_DELIVERY_STATE_TIMEOUT` observations (the shot ACK observers) and 234 parallel timeouts, while
  the harness streams 55,954 `rtc-diagnostic` events in 54 s. Locally the setup burst passes and
  the ACK path is the blocker; hosted, the setup burst fails first. Step 2a therefore takes the ACK
  path and the harness, step 2b the server engine and the handler cost.
- **Match window (ACK observers time out although shots arrive):** B1 (the director waits for the
  tree) amplified by B2 (ACK flood on the shared limiter) and B4 (8 s to fallback, retries re-flood),
  with the harness leaving ≈5 s for the last shot and its verification (H3) on pages doing O(history)
  work per event (H2).

or under 20 ACK submissions per second and 164/1,000 admissions; only 7 shots fell back to WS; the
per-session 20/s limiter, the breaker and the RTC data-channel queue emit no diagnostics, so they
are unobserved. Harness load rose to ≈9,000 events per second (180 per agent, 94 % ALM
diagnostics; 3,400 at 30), 75 % of events reached the control server more than 1 s late (up to
37 s), and 13 agents' recipe results never arrived, although the pages' own 5 s stats cadence and
trivial command latencies stayed on time. Ranked causes for step 2b: (1) director placement and
tree depth (topology planning), (2) per-hop ALM cost and retry churn at hub relays, (3) the harness
diagnostic volume making the evidence lossy, (4) unobserved limiter/breaker/queue state needing a
diagnostic before it can be ruled in or out.

## 2. GitHub Free review

The repository is public, so standard-runner minutes are free; the hard limits are ≈20 concurrent
jobs per account (the workflow caps agent jobs at 19 and needs every shard at once), 4 vCPU/16 GiB
standard runners (larger runners are a paid plan), one shared concurrency group across both modes
and the Hetzner workflow, and the `production` environment gate.

Verdict: GitHub is not what blocks the cohorts; the Hetzner API's setup burst and ACK return path
are. The recipes run locally first through the all-local lifecycle (`CI=1`, memory API, headless
SPA, mesh min size N+1, unbounded retention; the runbook's single command omits the `--admit`
step and four required variables and is corrected in step 2a). On this Mac (12 cores, 96 GiB) 15
agents fit easily, 30 is plausible, 50 fits in memory; the API main thread stays the bottleneck.
Measured on the step 2a head (local, this Mac): the 15-agent run passes (15/15 recipes, 231/231
assertions); the 30- and 50-agent runs fail at setup because every co-located agent registers and
logs in from one IP and the API's per-IP limits are 20 registrations and 30 logins per minute
(`authentication.rateLimits.registrationIp`/`loginIp`): the last 10 and 30 registrations are
refused, the page shows the refusal, the worker still registers the agent with the control server,
and the recipe's first login reports a misleading 401. The lifecycle's API env block raised only
the per-user login limit; so does the hosted controller's env, which co-locates agents on one VM.
Step 2a raises the two per-IP limits in both co-located lifecycles to the cohort ceiling (product
defaults unchanged) and makes a refused registration fail the agent at start.

Changes that only the maintainer can make and that the review recommends regardless: a deployment
branch policy or required reviewer on the `production` environment (any branch can read its secrets
today), deleting the plaintext Actions variable named like the password secret, and optionally a
`runs-on` input for a self-hosted all-local runner.
